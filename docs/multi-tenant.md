# 多租户与激活码

本文档说明集中托管模式下的账号模型、激活码流程、隔离边界和运维方式。

## 角色

| 角色 | 来源 | 权限 |
| --- | --- | --- |
| `owner` | 首次启动创建 `admin`，或从 `admin.json` 迁移已有账号 | 全部账号、租户管理、激活码管理、系统设置 |
| `tenant` | 激活码兑换或 owner 手动创建 | 只能管理自己名下的游戏账号和账号配置 |

会话保存在进程内存中，服务重启后所有用户需要重新登录。每次 API 请求都会实时校验租户状态和到期时间，因此延期、停用会立即生效。

## 数据文件

数据目录默认是 `core/data`（Docker 为 `/app/core/data`）：

| 文件 | 内容 |
| --- | --- |
| `users.json` | owner 与租户账号、密码哈希、状态、到期时间、账号配额和新版激活码核销记录 |
| `activation-codes.json` | 激活码哈希和密文、兑换条件、批次、指定租户、换发关系、吊销时间及旧版兑换记录 |
| `activation-code-key` | 用于读取完整激活码的密钥，随数据目录一起安全备份 |
| `owner-bootstrap-password.txt` | 未配置初始密码时生成的随机密码，首次修改密码后删除 |
| `accounts.json` | 游戏账号；每个账号带 `ownerId`，旧数据自动归属 `owner` |
| `account-configs/` | 每个游戏账号的独立配置 |
| `login-attempts.json` | 登录失败锁定和 IP 限流记录 |
| `admin-audit.json` | 管理员读取完整码、调整激活码和管理租户等最近 2000 条操作记录 |

新生成或换发的激活码同时保存 SHA-256 哈希和加密后的完整码。管理员可从列表复制单张码，或打开批次复制、导出待兑换的码。旧版本仅保存哈希的码无法恢复完整值，未兑换的旧码可换发。

## 激活码流程

1. owner 在「用户与激活码 → 激活码」中生成批次。
   - 类型：`new`（新用户）或 `renew`（续费）。
   - 有效天数从新用户兑换起算。续费在当前到期时间与兑换时间中取较晚者，再加有效天数。
   - 账号配额是租户可添加的游戏账号上限。续费时仅在续费码配额更高时调整。
   - 兑换截止：超过该时间后未兑换的码失效，可选。
   - 指定租户：续费码可指定一位租户，仅该租户可以兑换。
2. 朋友访问 `/redeem`，填写激活码、用户名和密码，成功后自动登录。
3. 到期后：
   - 受保护的 API 会拒绝过期租户，首次识别到期时返回 `403 tenant_expired`；
   - 后台每 10 秒巡检一次，停止该租户正在运行的 worker，并断开实时连接；
   - 朋友在 `/renew` 输入用户名、密码和续费码，成功后恢复。
4. owner 可以延期、停用、重置密码、踢下线或删除租户。删除租户会同时停止并删除其名下账号。

在激活码列表点击「管理」可修改未兑换码的天数、配额、截止时间和备注，或吊销、换发。换发会吊销旧码并链接新旧记录，保留原权益和指定租户，已过期的兑换截止时间会清除。点击批次可集中吊销其中未兑换的码。已兑换码可补充备注，发放的权益仍可从关联租户的管理面板调整。

## 隔离边界

- 账号归属：`Account.ownerId`。所有账号级接口通过 `getAccId` / `resolveAccId` 统一校验归属；租户无法用其他租户的账号 ID 探测数据。
- 账号列表：`/api/accounts` 只返回当前用户可见账号。
- 日志：`/api/logs`、`/api/account-logs` 按可见账号过滤。
- 实时推送：租户仅订阅自己名下的账号，每次投递都校验当前会话和账号归属。
- 扫码登录：面板为每个租户、每个平台保留一项待处理任务。任务绑定发起会话和目标账号，QQ 按到达顺序使用 NapCat，微信任务独立执行。删除账号会关闭其重登任务，停用或到期会清理该租户的扫码任务。
- 全局设置：运行环境、登录设置、下线提醒、主题、调度器状态仅 owner 可读写。租户读取登录设置时只返回可用开关，不返回 NapCat 地址和签名。
- 账号配额：租户新建账号时校验 `maxAccounts`。

## 环境变量

| 变量 | 默认值 | 说明 |
| --- | --- | --- |
| `HIDE_UPSTREAM_LINKS` | `0` | `1` 隐藏面板中的上游 GitHub 链接 |
| `SITE_NAME` | `QQ农场智能助手` | 登录页/兑换页/侧边栏站点名称 |
| `SESSION_TTL_HOURS` | `168` | 会话有效期（小时） |
| `DEFAULT_MAX_ACCOUNTS` | `3` | 新激活码默认账号配额 |
| `ADMIN_PASSWORD` | 无 | 初始化管理员或替换旧版已知默认密码，留空时生成随机初始密码 |
| `TRUSTED_PROXIES` | 无 | 可信反向代理的 IP 或 CIDR，逗号分隔。启用后 Express 从可信代理链获取客户端 IP |
| `FARM_RESTORE_INTERVAL_MS` | `1500` | 托管恢复队列中，每次启动的间隔（毫秒） |

## 托管恢复

- 新增账号时提交登录 Code、重新登录或点击启动托管，会保存该账号的托管意图。手动停止会关闭自动恢复。升级前已存在的账号没有这项记录，通过新版本启动一次即可保存。
- 服务启动、到期租户续费或停用租户恢复后，会按队列分批启动已启用、租户当前有效且有可用 Code 的账号。服务向 Worker 发送一次性 Code 前会先记录使用状态，已经使用或被拒绝的 Code 会提示重新扫码或更新。进程恢复后，游戏连接仍取决于登录码是否有效。
- 管理员可从管理台的到期提醒直接为对应租户延期或发续费码。租户首页会显示托管状态、最近一次异常和到期时间。
- 「用户与激活码 → 操作记录」可按类型和目标查询。记录保留账号、码或批次标识用于追踪，不包含完整码和密码。

### 扫码任务

- 在 QQ 或微信页填写可选备注后点击「获取二维码」。扫码确认后由服务端校验权限、保存账号，再交给 Worker。重登沿用指定账号和原平台。浏览器可在授权开始后离开页面，保存会继续。
- 扫码队列与二维码保存在进程内。等待通道最多 4 分钟，尚未扫码且 30 秒没有客户端查询的任务将自动释放。已结束任务的结果最多保留 5 分钟，供同一会话重试查询。同一个请求标识重复提交会返回原任务。
- 面板重启后，未结束的扫码任务需要重新发起。下一张 QQ 码发出前会检查 NapCat 是否仍有任务或需要恢复注销。每项任务使用发码时的 NapCat 配置完成查询和注销。服务日志记录状态、错误类型和分阶段耗时。

#### QQ 授权服务就绪修复

- 使用独立 `qq-miniapp-auth` 容器的部署，可以从本仓库运行 `bash tools/qq-auth-recovery/install.sh /opt/services/qq-farm-classic`。脚本校验授权服务源码提交 `ec3123a06ca09ebd7759cc61e96801f1fde6c78e`，只在空闲时套用 Compose 覆盖并重建 `qq-auth`，启动失败时恢复之前的容器配置。
- 清理上一轮 QQ 登录时，授权服务先检查 NapCat 的登录状态。仅在明确没有已登录或已确认的会话时，才清除遗留的注销失败标记。桥接插件断开或 Worker 重启后，需要重新核实退出状态才能释放通道。授权服务以 `qq_logout` 事件记录核验结果。
- QQ 客户端确认退出后，下一轮以实际生成新码验证就绪。取码失败且确认 NapCat 离线时，每轮至多尝试一次 Worker 恢复。仍无法取码时，宿主机的 `qq-farm-qr-recovery.path` 接受当前授权流程验证过的请求，按原镜像重建 NapCat 一次，保留持久化挂载。下一次恢复由新的取码请求触发，间隔依次为 5、15、45 分钟，最长 60 分钟。成功生成新码后重置间隔。授权服务健康接口的 `qrReadiness`、`qrRetryAfterMs` 和 `qrRecoveryRetryAfterMs` 分别记录就绪状态、取码退避和恢复退避。
- 覆盖文件随部署保留在 `auth-deploy/recovery/current`。维护授权容器时沿用两份 Compose 文件，或重新运行安装脚本。农场容器和持久化目录沿用现有部署流程。

### 备份与恢复演练

1. 暂停服务写入后，备份整个数据目录。使用仓库的 Compose 配置时，业务数据位于 `qq-farm-data` 卷，日志位于独立的 `qq-farm-logs` 卷。限制备份文件的访问权限。
2. 将同一份备份解包至新的目录或卷，用同版本服务读取。先用测试账号和模拟 Worker 验证租户、激活码解密、核销记录、托管开关和管理员操作记录。
3. 确认可用登录 Code 对应的账号按队列启动，手动停止和租户到期的账号保持停止，已使用的 Code 显示待重新登录。确认后再将验证过的数据交给单个运行实例。

## 运维建议

- 初始密码由服务器数据目录读取。使用随机初始密码登录后，设置新密码方可使用管理面板。
- 定期备份整个数据目录。激活码核销记录、激活码清单和密钥应从同一份备份恢复。运行实例对数据目录独占读写。
- 不要把 `core/data` 暴露为静态目录，也不要在日志中输出激活码明文。
- 生产环境建议放在 HTTPS 反向代理之后，并限制管理端口的来源 IP。
- 租户的游戏登录凭据集中保存在 `accounts.json` 中；如果用户规模扩大，建议进一步按租户拆分数据目录或加密敏感字段。
- 本项目没有内置支付、自动发卡或退款流程；激活码由 owner 线下发放。
- 游戏自动化本身可能违反游戏服务条款，集中托管会放大账号和合规风险，请自行评估。
